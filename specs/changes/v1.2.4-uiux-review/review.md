# 审视之眼 Pro V1.2.4 — UI/UX 交互审查报告

> 审查人：OpenSpec / Claude
> 审查日期：2026-05-25
> 审查对象：`app.py`（3160 行）、`utils.py`、`export_utils.py`

---

## 一、信息架构与布局

### 1.1 A 区底部功能堆叠过重 — 建议拆分侧边栏

**现状**：A 区纵向排列了：统计卡片(6 个) → 筛选按钮(6 个) → 分页列表 → 抽检复核 → 导出管理 → AI 预识别 → 更多设置 → 分类管理。用户需要大量滚动才能找到常用功能。

**问题**：
- 统计卡片占 3 行 × 2 列 = 6 个 metric，高度约 180px，挤压了下方列表空间
- 「抽检复核」「导出管理」「AI 预识别」「更多设置」「分类管理」全部以 expander 形式堆在 A 区底部，信息层级不清晰
- 用户在质检过程中最频繁操作的是「筛选 + 列表选择」，但这两项被统计卡片推到了中下部

**建议**：
- 将统计卡片改为**单行紧凑横排**（6 个 metric 一行），或改为「已完成/总数」+ 合格率的**2 卡片模式**，筛选时再展开详情
- 将「抽检复核」「导出管理」「AI 预识别」「更多设置」「分类管理」整合为 **A 区顶部的 Tab 导航**（📋 列表 / 📊 抽检 / 📤 导出 / ⚙️ 设置），减少纵向滚动
- 列表区应占据 A 区 **60% 以上高度**

### 1.2 C 区操作面板信息密度不均

**现状**：C 区纵向排列：信息栏 → 错误截图 → 导航 → L1/L2 分类 → 备注 + 保存/提交 → 状态按钮(2×2) → 快捷标签 → 标签管理。

**问题**：
- 「错误截图」区域（粘贴按钮 + 3 张预览图）占据大量纵向空间，但多数情况下用户不需要截图
- 「保存」和「提交并下一条」按钮在 form 内部，但状态按钮(合格/不合格/修改后合格/待定)在 form 外部，操作顺序不连续
- 用户的典型操作流是：看图 → 选状态 → 选分类 → 提交。但状态选择在最底部，与提交按钮之间隔着快捷标签

**建议**：
- 将「错误截图」区域默认折叠（`expanded=False`），仅在需要时展开
- 将状态按钮(2×2 网格)上移到导航按钮下方、L1/L2 分类之前，形成「**状态 → 分类 → 备注 → 提交**」的自然操作流
- 「快捷标签」移到备注框上方（分类之后、备注之前），标签选择和备注关联更紧密

### 1.3 冷启动页面功能入口不明确

**现状**：冷启动页面显示呼吸眼动画 + 操作员名称输入 + 路径输入 + 加载按钮 + 标注员确认复选框 + 更多设置 expander。

**问题**：
- 动画占 600px 高度，实际操作区在页面下方，用户需要滚动
- 「更多设置」里的布局调节、视图切换、扫描规则、快捷键等在冷启动时不需要
- 标注员确认功能的 checkbox 说明文字过长（73 字），理解成本高

**建议**：
- 动画高度从 600px 减至 400px，或将操作区与动画并排显示
- 冷启动页面只保留：操作员名称 + 路径 + 加载按钮，其他设置移除
- 标注员确认功能的说明精简为一句话 + tooltip 详情

## 二、操作效率

### 2.1 提交流程需要 3 次点击 + 滚动

**现状**：用户需要：
1. 滚动到 C 区底部选择状态（合格/不合格等）
2. 滚动回中部选择 L1/L2 分类
3. 滚动到最底部点击「提交并下一条」

**建议**：
- 如果状态按钮上移（见 1.2），操作流变为：选状态 → 选分类 → 填备注 → 提交，无需来回滚动
- 考虑为常用操作组合提供**一键快捷**：如「合格 + 提交」合并为一个按钮

### 2.2 列表项点击后触发全局 rerun

**现状**（`app.py:1957-1969`）：A 区 radio 选择列表项后，调用 `st.rerun(scope="app")` 触发全页面刷新。这会导致：
- B 区图片重新渲染（闪烁）
- C 区表单状态丢失
- 用户感知到明显延迟

**建议**：
- A 区列表选择应只触发 B 区和 C 区的 fragment 更新，避免全局 rerun
- 使用 `@st.fragment` 的局部更新机制，让列表选择只刷新 B 区和 C 区

### 2.3 标签选择触发全局 rerun

**现状**（`app.py:2046-2049`）：标签 pills 选择变化时调用 `st.rerun()`，导致整个页面刷新。

**建议**：
- `render_tag_selector` 已经是 `@st.fragment`，标签变化应只在 fragment 内部处理，不调用全局 `st.rerun()`
- 使用 `st.session_state` 标记待同步状态，在下一次自然 rerun 时同步到备注

### 2.4 分类管理面板操作繁琐

**现状**（`app.py:1745-1817`）：每个 L1/L2 分类项需要：编辑文本框 → 点击保存按钮。添加新分类需要：输入文本 → 点击添加按钮 → 点击保存配置按钮。

**问题**：
- 编辑后必须手动点击「💾 保存配置」才能生效，容易忘记
- 删除操作没有确认，直接 `st.rerun()`
- L1 和 L2 管理在同一个 expander 内，L2 依赖先选择 L1

**建议**：
- 编辑后自动保存（debounce），去掉「💾 保存配置」按钮
- 删除操作增加确认步骤（tooltip 或二次点击）
- L1/L2 管理改为左右分栏布局，左侧 L1 列表，右侧对应 L2 列表

### 2.5 快捷键覆盖不完整

**现状**（`app.py:905-966`）：快捷键通过 JS 注入实现，仅覆盖：左右箭头(导航)、空格(提交)、1-4(视图切换)、反引号(系统查看器)。

**缺失**：
- 没有快捷键切换状态（合格/不合格等），这是最高频操作
- 没有快捷键保存（Ctrl+S 被浏览器占用）
- 没有快捷键撤销上一步操作
- 没有快捷键跳转到未检项

**建议**：
- 增加快捷键：`Q`=合格, `W`=不合格, `E`=修改后合格, `R`=待定
- 增加快捷键：`N`=跳转下一个未检项
- 增加快捷键：`S`(无 Ctrl)=保存

## 三、视觉与反馈

### 3.1 状态颜色体系不一致

**现状**：状态颜色映射：
- 合格 = 🟢 绿色
- 不合格 = 🔴 红色
- 修改后合格 = 🔵 蓝色
- 待定 = 🟡 黄色
- 未检 = ⚪ 白色

**问题**：
- L1 分类用 🔵 前缀，L2 分类用 🟢 前缀，与状态颜色冲突（🔵 既是「修改后合格」又是 L1 标记）
- 筛选按钮和状态按钮使用相同的 2×2 网格布局，视觉上难以区分「筛选」和「判定」
- AI 质检结果用 ✅/❌ 图标，与人工状态的 🟢/🔴 含义相近但体系不同

**建议**：
- L1/L2 分类 pills 去掉颜色前缀 emoji，改用无色标记或统一用一种中性色
- 筛选按钮和状态按钮在视觉上做区分：筛选按钮用 outline 样式，状态按钮用 filled 样式
- AI 质检结果区域增加明显的「AI」标签，与人工判定区分开

### 3.2 导出确认弹窗缺少关键信息

**现状**（`app.py:2766-2805`）：导出确认面板显示统计数字，但缺少：
- 导出目标路径预览
- 预计导出文件大小
- 导出操作的预计耗时

**建议**：
- 在确认面板中显示导出目标路径
- 显示预计导出组数和每组平均大小
- 导出过程中显示进度条和 ETA（当前只有 `st.status`）

### 3.3 批量操作无进度反馈

**现状**（`app.py:1564-1611`）：`export_qualifies_with_check` 使用 `st.status` 显示进度，但：
- 每 3 条才更新一次 UI，用户感知到卡顿
- 没有 ETA（预估剩余时间）——实际上有但显示在 label 中，不够醒目
- 复制失败的文件夹只在最后汇总显示，过程中用户不知道哪些失败了

**建议**：
- 增加进度百分比的 `st.progress()` 条
- ETA 单独显示为 caption，不要混在 status label 中
- 失败项实时追加显示，不要等到最后

### 3.4 Toast 消息过于简短

**现状**（`app.py:2313-2315`）：保存/提交成功后只显示 `st.toast("✓ 已保存")` 或 `st.toast("✓ 已提交")`。

**建议**：
- Toast 中显示当前进度：`✓ 已保存 (42/150)`
- 提交后显示下一条 ID：`✓ 已提交，下一条: 00123456`
- 保存失败时 toast 改为 `st.error()` 并保持可见

## 四、性能优化

### 4.1 图片缓存策略可优化

**现状**（`app.py:141-174`）：`get_display_image_bytes` 使用 `session_state` 字典缓存，限制 50 条 / 100MB。

**问题**：
- 缓存 key 包含 `os.path.getmtime()`，每次访问都要读取文件系统，对网络驱动器（UNC 路径）影响大
- 缓存淘汰策略是 FIFO（删除最早条目），不是 LRU
- 每次切换图片都创建新的 `BytesIO` 对象

**建议**：
- 缓存 mtime 改为在扫描时一次性读取并存储在 group 数据中
- 淘汰策略改为 LRU（使用 `collections.OrderedDict` 的 `move_to_end`）
- 考虑将缩放后的图片 bytes 直接缓存为 base64 字符串，避免重复 BytesIO 转换

### 4.2 CSV 读写频率过高

**现状**：
- 每次切换列表项都会调用 `_get_df()` 读取 CSV（虽然有缓存）
- 每次保存都读取整个 CSV → 修改一行 → 写回整个文件（`app.py:1025-1045`）
- `get_record_status_map()` 在 A 区 fragment 每次渲染时调用，触发 CSV 读取

**建议**：
- `_get_df` 缓存命中时直接返回副本，避免每次都 `.copy()`
- `save_to_disk` 改为追加写入（append mode），定期合并去重
- `get_record_status_map` 结果也应缓存，在 `save_to_disk` 后失效

### 4.3 预加载策略可优化

**现状**（`app.py:176-192`）：`preload_next_images` 预加载当前索引后 N 张图的原图和显示图。

**问题**：
- 预加载是同步阻塞的，在主线程中执行
- 只预加载「下一条」方向，不预加载「上一条」
- 没有根据用户操作模式调整预加载策略（快速连续点击时预加载无意义）

**建议**：
- 预加载改为异步（使用 `threading.Thread` 或 `asyncio`）
- 增加反向预加载（上一条方向 1-2 张）
- 增加防抖：用户快速点击时不触发预加载

### 4.4 `st.rerun()` 调用过于频繁

**现状**：全代码中有 **15 处** `st.rerun()` 调用，包括：
- 标签选择变化
- 筛选按钮点击
- 分类管理增删
- 设置变更
- 导出操作
- 页面跳转

**问题**：每次 `st.rerun()` 都会重新执行整个 `run()` 方法（3160 行），即使大部分逻辑不变。

**建议**：
- 优先使用 `@st.fragment` 实现局部更新
- 标签选择、筛选按钮、设置变更等场景应避免全局 rerun
- 只在必须刷新 B 区/整体布局时才使用 `st.rerun()`

## 五、交互细节

### 5.1 分页列表的当前页指示不够明显

**现状**（`app.py:1894-1973`）：分页按钮使用 `st.button` 实现，当前页用 `type="primary"` 高亮。

**问题**：
- 页码按钮和筛选按钮样式完全相同，容易混淆
- 当前选中项在列表中没有特殊高亮（只有 radio 的选中状态）
- 切换页码后列表位置没有自动滚动到顶部

**建议**：
- 当前选中列表项增加背景色高亮（不仅靠 radio 选中态）
- 页码按钮组增加「跳转到第 N 页」的输入框（当总页数 > 10 时）
- 切换页码后自动滚动列表到顶部

### 5.2 四宫格视图下图片操作按钮过小

**现状**（`app.py:2464-2505`）：四宫格模式下，每张图片下方有分辨率 caption 和 📂 按钮，通过 CSS 将按钮缩到 0.7rem。

**问题**：
- 📂 按钮太小（0.7rem），在触摸设备上几乎无法点击
- 双击图片打开系统查看器的交互通过 JS 注入实现，不够可靠
- 没有图片放大预览的快捷方式（需要切到单图模式或打开系统查看器）

**建议**：
- 📂 按钮保持可点击大小（至少 0.85rem），hover 时显示完整提示
- 四宫格下点击图片直接弹出高清大图 dialog（复用 `show_large_image`）
- 双击功能保留作为快捷方式，但不应是唯一入口

### 5.3 错误截图粘贴功能缺乏引导

**现状**（`app.py:2105-2136`）：错误截图区域使用 `streamlit-paste-button` 库，用户需要先截图到剪贴板，再点击粘贴按钮。

**问题**：
- 没有提示用户如何截图（Win+Shift+S 或 Print Screen）
- 粘贴按钮达到 3 张上限后显示「✅ 已达3张上限」，但没有提示用户可以删除单张
- 截图预览图没有删除单张的功能，只能「🗑️ 清空截图」全部删除

**建议**：
- 粘贴按钮区域增加 caption 提示：「截图后按 Ctrl+V 粘贴」
- 增加单张删除按钮（每张预览图右上角的 × 按钮）
- 达到上限后仍然允许替换（删除一张再粘贴新的）

### 5.4 L1/L2 分类选择 sticky 行为不透明

**现状**（`app.py:2166-2190`）：L1 选择有 sticky 机制（切换下一条时保留上次选择），L2 在 L1 变化时清空。

**问题**：
- 用户不知道 sticky 行为的存在，可能误以为数据丢失
- L2 清空时没有提示
- 如果当前记录已有 L1/L2，切换到该记录时应恢复记录值而非使用 sticky 值

**建议**：
- 在 L1/L2 区域增加 caption：「默认沿用上一条选择」
- L2 清空时显示 toast 提示
- `sync_state_from_history` 中的 L1/L2 恢复逻辑应优先于 sticky

## 六、移动端与响应式

### 6.1 三栏布局在窄屏下不可用

**现状**：三栏布局使用固定百分比（`layout_width` 默认 64%），在窄屏下三栏重叠或溢出。

**建议**：
- 检测视口宽度，窄屏下自动切换为单栏 tab 布局
- 或提供「移动端模式」开关，将 A/C 区折叠为底部抽屉

### 6.2 CSS 使用 `!important` 过多

**现状**（`app.py:2901-2997`）：自定义 CSS 中大量使用 `!important` 覆盖 Streamlit 默认样式，共 **47 处**。

**问题**：
- Streamlit 版本升级后默认样式变化可能导致自定义 CSS 失效
- `!important` 优先级过高，调试困难

**建议**：
- 使用更具体的选择器减少 `!important` 使用
- 将自定义 CSS 抽取到独立的 `.css` 文件
- 增加 Streamlit 版本兼容性检测

## 七、可访问性

### 7.1 缺少键盘导航支持

**现状**：快捷键仅覆盖 6 个操作，Tab 键导航顺序依赖 Streamlit 默认行为。

**建议**：
- 为所有按钮增加 `tabindex` 和 `aria-label`
- 状态按钮支持 Enter/Space 触发
- 列表支持上下箭头键导航

### 7.2 颜色对比度不足

**现状**：部分文字使用 `#999`（浅灰）作为颜色，在白色背景上对比度约为 2.8:1，低于 WCAG AA 标准（4.5:1）。

**建议**：
- 将浅灰色文字改为 `#666` 或更深
- 确保所有交互元素的对比度符合 WCAG AA 标准
